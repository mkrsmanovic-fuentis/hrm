The API is designed contract-first. One OpenAPI 3.1 spec, `docs/api-reference/openapi.yaml`, describes every endpoint. The frontend is built against it through a [mocked API](/developer-guide/mock-api), and the real backend will implement it.

The endpoint pages in this section are generated from the spec. To change an endpoint, change the spec, not the pages. The playground needs a running backend, so it cannot send requests yet.

## Conventions

Every endpoint follows these rules. New endpoints must too.

### URLs

- The base path is `/api/v1`. Paths in the spec are written without it, for example `/topics` means `/api/v1/topics`.
- Resources are plural nouns in kebab-case: `/topics`, `/questionnaire-versions`. One record is addressed by its ID: `/topics/{topicId}`.
- A resource that exists once per user is singular: `/organization`.
- Path parameters are named after the resource, in camelCase: `{topicId}`, not `{id}`.
- Query parameters and JSON fields use camelCase. Enum values use snake_case, for example `not_started`.

### Organization

Every record belongs to an organization. The MVP has one organization, and the API exposes it as the **current organization**: the organization of the signed-in user, derived from the session.

- Organization IDs never appear in URLs or request bodies.
- Each record still carries `organizationId`, so the model supports more organizations later.
- Records of another organization behave as if they do not exist: the API answers `404`.

Get the current organization with `GET /api/v1/organization`.

### Shared fields

| Field | Type | Notes |
| - | - | - |
| `id` | `Id` | A UUID. Every record has one. |
| `organizationId` | `Id` | The owning organization. |
| `createdAt` | `Timestamp` | Date and time in UTC, ISO 8601, for example `2026-11-10T09:30:00Z`. |
| `updatedAt` | `Timestamp` | When the record last changed. |
| `status` | `ActivityStatus` | `active` or `inactive`, on records that can be deactivated. Deactivating keeps the history. |

References to other records use the record name plus `Id`, for example `topicId`. Optional values are `null`, not left out.

### Authentication

Every endpoint needs a session token, sent as a bearer token:

```http
Authorization: Bearer <session token>
```

- The authentication endpoints, under `/api/v1/auth`, issue the token. Email and password come first; SSO can be added there later without changing any other endpoint.
- The rest of the API only checks the token. It never knows how the user signed in.
- Invite links to set a password are valid for 7 days. Password reset links are valid for 1 hour. See [Business rules](/developer-guide/business-rules#accounts-and-access).

The current session is a resource that exists once per user, so its URL is singular:

| Endpoint | Token | What it does |
| - | - | - |
| `POST /auth/session` | Not needed | Signs in with `email` and `password`. Answers `201` with a `Session`: `token`, `createdAt`, `expiresAt` and the signed-in `user`. |
| `GET /auth/session` | Required | Returns the current session. Answers `401` when the token is missing, unknown or expired. |
| `DELETE /auth/session` | Optional | Signs out. The token stops working at once. Always answers `204`, even without a valid token. |

- A session lasts **8 hours** from sign-in. Activity does not extend it. After `expiresAt`, every call with the token answers `401`.
- A wrong password, an unknown email and a user who has not set a password yet all get the same `401` with type `/problems/invalid-credentials`, so the answer does not reveal which emails have accounts.
- A deactivated user who enters the right password gets `403` with type `/problems/account-inactive`.
- When any other call answers `401`, the client drops its token and asks the user to sign in again.

See [Business rules](/developer-guide/business-rules#sign-in-and-sessions) for the sign-in rules and [Authentication](/developer-guide/authentication) for how the frontend uses them.

### Authorization

Each endpoint lists which roles may call it under **Access**. The [access matrix](/developer-guide/business-rules#access-by-role) is the full list.

- An endpoint that a role may not call answers `403` with type `/problems/forbidden`, before validating the request. For example an employee calling an administrator endpoint.
- Employees get only their own records. Lists leave out other users' records, and a record of another user answers `404`, like one that does not exist.
- Content an employee may not see, such as an inactive topic, is left out of lists and answers `404`.
- A `403` does not end the session. Only `401` asks the user to sign in again.

### Lists and pagination

List endpoints return one page at a time.

| Parameter | Default | Rules |
| - | - | - |
| `page` | `1` | Page number, starting at 1. |
| `pageSize` | `25` | From 1 to 100. |
| `sort` | Depends on the endpoint | A field name, with `-` in front for descending order, for example `-createdAt`. Each endpoint lists the allowed values. |

Filters are plain query parameters named after the field, for example `?status=active`. On records that can be deactivated, a list returns active and inactive records unless `status` is sent.

Lists that can be searched take `q`, a text search. It matches records whose searched fields contain the text, ignoring upper and lower case and spaces around it. Each endpoint says which fields `q` searches, for example the name.

The response is an envelope with the items and the page position:

```json
{
  "items": [{ "id": "…", "name": "Data Protection" }],
  "page": { "page": 1, "pageSize": 25, "totalItems": 7, "totalPages": 1 }
}
```

A page past the end returns an empty `items` list, not an error.

### Creating and changing records

Administrator endpoints that change data follow one pattern. [Departments](/api-reference/overview#departments-the-reference) are the first resource built on it.

| Request | Answer | What it does |
| - | - | - |
| `GET /departments` | `200` with a page | Lists records, with paging, filters, `q` and `sort`. |
| `POST /departments` | `201` with the record | Creates a record. |
| `GET /departments/{departmentId}` | `200` with the record | Reads one record. |
| `PATCH /departments/{departmentId}` | `200` with the record | Changes the fields sent. Fields left out stay as they are. |

- **Deactivate and reactivate with `PATCH`.** Send `{ "status": "inactive" }` to deactivate and `{ "status": "active" }` to reactivate. There are no separate deactivate endpoints, and records that can be deactivated have no `DELETE`: deactivating keeps their history.
- **Request bodies list only fields the client may set.** Each resource has a `<Entity>Create` and a `<Entity>Update` schema. They leave out `id`, `organizationId`, `createdAt`, `updatedAt` and derived fields. Unknown fields are rejected with `422`.
- **Text is trimmed.** Spaces around text fields are removed before they are checked and saved. An optional text field sent empty is saved as `null`.
- **Derived fields** are computed by the server and marked read-only in the spec, for example a department's `employeeCount`. They are never sent in requests and never stored.
- **Unique fields** are unique within the organization, among active and inactive records. A value already in use answers `409` with type `/problems/conflict`; its `errors` names the field with code `not_unique`, so a form can show the message next to it.
- **Invalid fields** answer `422` with every invalid field in `errors`, with `location` set to `body`.
- **Administrator only.** An employee gets `403` before the body is validated.
- **Audit log.** Every successful change is logged. See [Audit log](/developer-guide/business-rules#audit-log).

#### Departments, the reference

```http
POST /api/v1/departments
Content-Type: application/json

{ "name": "Legal", "description": "Contracts and compliance." }
```

```http
HTTP/1.1 201 Created

{ "id": "…", "organizationId": "…", "name": "Legal", "description": "Contracts and compliance.",
  "status": "active", "employeeCount": 0, "createdAt": "…", "updatedAt": "…" }
```

A duplicate name:

```json
{
  "type": "/problems/conflict",
  "title": "Conflict",
  "status": 409,
  "detail": "A department named Finance already exists.",
  "errors": [
    {
      "location": "body",
      "field": "name",
      "code": "not_unique",
      "message": "A department with this name already exists."
    }
  ]
}
```

### Errors

Errors use the problem format from [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457), with the content type `application/problem+json`:

```json
{
  "type": "/problems/not-found",
  "title": "Not found",
  "status": 404,
  "detail": "Topic 2f0c1a7e-3b6d-4c1e-9f7a-5d2e8b4c6a10 was not found.",
  "instance": "/api/v1/topics/2f0c1a7e-3b6d-4c1e-9f7a-5d2e8b4c6a10"
}
```

Clients branch on `type`. `title` and `detail` are for people.

| Status | `type` | When |
| - | - | - |
| 400 | `/problems/bad-request` | The request cannot be read, for example invalid JSON. |
| 401 | `/problems/unauthenticated` | No valid session token. The user must sign in. |
| 401 | `/problems/invalid-credentials` | Sign-in only: the email and password do not match an account that can sign in. |
| 403 | `/problems/account-inactive` | Sign-in only: the password is right, but the account is deactivated. |
| 403 | `/problems/forbidden` | Signed in, but not allowed. For example an employee calling an administrator endpoint. |
| 404 | `/problems/not-found` | The record does not exist in the current organization. |
| 409 | `/problems/conflict` | The request conflicts with the current state, for example a name already in use, a second open assignment for the same questionnaire, or a questionnaire that cannot be activated yet. A conflict about a field names it in `errors`, with code `not_unique`. A refused activation lists its reasons in `activationProblems`. |
| 422 | `/problems/validation-failed` | One or more fields are invalid. See below. |
| 500 | `/problems/internal-error` | Something went wrong on the server. |

Validation errors list every invalid field in `errors`:

```json
{
  "type": "/problems/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "detail": "1 field is invalid.",
  "errors": [
    {
      "location": "query",
      "field": "pageSize",
      "code": "out_of_range",
      "message": "Must be between 1 and 100."
    }
  ]
}
```

- `location` is `body`, `query`, `path` or `header`.
- `field` names the field. Nested body fields use dots and indexes, for example `questions[2].text`.
- `code` is one of `required`, `invalid_type`, `invalid_format`, `invalid_value`, `out_of_range`, `too_short`, `too_long` or `not_unique`. `not_unique` comes with a `409`, not a `422`.
- `message` can be shown next to the field.

#### A questionnaire that cannot be activated yet

Activating a questionnaire (`PATCH /questionnaires/{questionnaireId}` with `{ "status": "active" }`) runs the [checks before activation](/developer-guide/business-rules#checks-before-activation). When any fails, the answer is `409` and nothing changes. `activationProblems` lists **every** problem, so a client can show them all and link to each question:

```json
{
  "type": "/problems/conflict",
  "title": "Conflict",
  "status": 409,
  "detail": "This questionnaire can't be activated yet. Fix 3 problems first.",
  "activationProblems": [
    {
      "code": "too_few_answer_options",
      "questionId": "7b1e2c4d-5a6f-4b8c-9d0e-1f2a3b4c5d6e",
      "questionNumber": 2,
      "message": "Question 2 has fewer than 2 answer options. Add at least 2."
    },
    {
      "code": "no_correct_answer",
      "questionId": "7b1e2c4d-5a6f-4b8c-9d0e-1f2a3b4c5d6e",
      "questionNumber": 2,
      "message": "Question 2 has no correct answer. Choose one."
    },
    {
      "code": "topic_inactive",
      "questionId": null,
      "questionNumber": null,
      "message": "The topic Clean Desk Policy is inactive. Choose another topic, or reactivate the topic."
    }
  ]
}
```

- `code` is one of `no_questions`, `question_text_missing`, `too_few_answer_options`, `answer_option_text_missing`, `no_correct_answer`, `several_correct_answers` or `topic_inactive`. Clients branch on it.
- `questionId` and `questionNumber` name the question in the current version: its ID, and its position from 1, as administrators see it. Both are `null` for a problem with the whole questionnaire: `no_questions` and `topic_inactive`.
- A question can have several problems. An empty answer option gives one problem for each empty option.
- `message` names the question and says how to fix it. It can be shown as it is.
- Problems come question by question, in order, then the topic.
- Each questionnaire also has the same list as its derived `activationProblems`, so a client can show it before trying. It is always empty for an active questionnaire.

## Adding an endpoint

Follow the steps in [Mock API](/developer-guide/mock-api#add-an-endpoint). In the spec:

- Give the operation an `operationId` in camelCase, one tag, and `x-mint: *spec-status` so its page shows the "Specification, not yet implemented" banner.
- Reuse the shared parameters (`Page`, `PageSize`), schemas (`Id`, `Timestamp`, `ActivityStatus`, `PageInfo`) and error responses under `components`, including `NotUnique` for a `409` on a unique field.
- Name list responses `<Entity>Page`, and request bodies `<Entity>Create` and `<Entity>Update` with `additionalProperties: false`.
- Mark derived fields `readOnly: true` and start their description with "Derived.".

See the [Data model](/developer-guide/data-model) for the fields of every entity.
