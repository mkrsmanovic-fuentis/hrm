Users sign in with email and password and get a session token. The frontend sends the token with every API call. The mock API checks it on every endpoint except sign-in and sign-out, as the real backend must.

The login page offers two of them for one-click sign-in, and the user menu switches between them:

- Deactivated users, such as `sofia.lindqvist@brightwater.example`. With the right password they get **Account deactivated**.

The demo password and the two accounts are set in `environment.demo` in `src/environments/environment.ts`. The mock's password is `DEMO_PASSWORD` in `src/mocks/seed/people.seed.ts`. A test checks that both demo accounts can sign in. Set `environment.demo` to `null` to hide the demo section and the role switch, for example with a real backend.

## How it works

<Steps>
  <Step title="Sign in">
    The login page (`src/app/features/login/`) calls [`POST /auth/session`](/api-reference/overview#authentication) with the email and password. The answer is a `Session`: the token, when it was created, when it expires, and the signed-in user. Then it opens the `returnUrl`, or the user's home page. A `returnUrl` in the other role's area also opens the user's home page instead of **No access**, for example when an employee signs in where an administrator's session ended.
  </Step>
  <Step title="The session is kept in the browser">
    `AuthService` (`src/app/core/auth/auth.service.ts`) stores the session in `localStorage` under `hrm.session`, so it survives a reload. On load, a session past its `expiresAt` is dropped.
  </Step>
  <Step title="The token goes with every API call">
    `authInterceptor` adds `Authorization: Bearer <token>` to every request to the API base URL. Other requests, such as assets, get no token.
  </Step>
  <Step title="A 401 signs the user out">
    When any API call answers `401`, the interceptor clears the session and opens `/login?returnUrl=<current page>`. After signing in, the login page returns there. The failed sign-in itself also answers `401`; the interceptor leaves that one to the login page.
  </Step>
  <Step title="The session ends on time, even on an open page">
    `AuthService` sets a timer for the session's `expiresAt`. When it fires, the session is cleared and `/login?returnUrl=<current page>` opens, even if the user is only reading a page.
  </Step>
  <Step title="Tabs share the session">
    Every tab of the app reads the same `hrm.session`. `AuthService` listens to the browser's `storage` event, so a change in one tab reaches the others:

    | In one tab | The other tabs |
    | - | - |
    | Sign out, or the session expires | Sign out and open `/login?returnUrl=<current page>`. |
    | Sign in, or switch the demo role | Take over the new session and open its home page. |

    In the mock, the tabs also share the mock data, so every tab knows the sessions the others started. See [Several tabs share the data](/developer-guide/mock-api#several-tabs-share-the-data).

    When another tab signs in while this tab shows the login page, this tab opens the login page's `returnUrl`, as if it had signed in itself.
  </Step>
  <Step title="Guards protect the routes">
    `signedInGuard` sends signed-out users, and users whose session has expired, to `/login`. `signedOutGuard` sends signed-in users from `/login` to their home page. Every page behind sign-in is a child of the shell route in `src/app/app.routes.ts`, which runs `signedInGuard` on every navigation. `roleGuard` keeps each role to its own area; see [Roles and access](/developer-guide/access-control).
  </Step>
  <Step title="The shell checks the session once per load">
    The shell calls `GET /auth/session` when it starts. If the API no longer knows the token, for example after a mock reset, the `401` signs the user out.
  </Step>
  <Step title="Sign out">
    The user menu calls `DELETE /auth/session`, then clears the session locally and opens `/login`. The session ends locally even if the call fails.
  </Step>
</Steps>

### Use it in a feature

Read the signed-in user and role from `AuthService` signals. Import from `core/auth`.

```ts
private readonly auth = inject(AuthService);

readonly user = this.auth.user;   // Signal<User | null>
readonly role = this.auth.role;   // Signal<'administrator' | 'employee' | null>
```

Pages behind sign-in need no extra code for sign-in: add them to a role's area and the guards cover them. See [How a feature adds a page and a nav entry](/developer-guide/access-control#how-a-feature-adds-a-page-and-a-nav-entry).

### Role switch for demos

**Switch to employee** and **Switch to administrator** in the user menu sign out, then sign in as the demo account of the other role, and open that role's home page. They appear only when `environment.demo` has an account for the other role.

## Rules

- A session lasts 8 hours from sign-in. Activity does not extend it.
- Only active users who have set a password can sign in.
- See [Business rules](/developer-guide/business-rules#sign-in-and-sessions) for the full list, including what the real backend must do.

## Mock behavior

| Request | Answer |
| - | - |
| `POST /auth/session`, right email and password | `201` with the session. Updates the user's `lastSignedInAt`. |
| `POST /auth/session`, wrong password, unknown email, or no password set yet | `401`, type `/problems/invalid-credentials`. |
| `POST /auth/session`, deactivated user with the right password | `403`, type `/problems/account-inactive`. |
| `POST /auth/session`, missing email or password, or an email without `@` | `422`, with every invalid field in `errors`. |
| `GET /auth/session` with a valid token | `200` with the session. |
| `DELETE /auth/session` | `204`, with or without a valid token. The token stops working. |
| Any other endpoint without a token, with an unknown token or with an expired one | `401`, type `/problems/unauthenticated`. |

- Sessions are stored in the `sessions` table of the mock database, so they survive a reload. `?mock-reset` empties it, which signs everyone out on their next API call.
- Simulation flags apply to the authentication endpoints too. `?mock-error=server` also makes sign-in fail. To test errors on one area while staying able to sign in, add a scope, for example `?mock-error=server&mock-scope=/topics`.
- `?mock-delay=2000&mock-scope=/auth` slows down sign-in, to see the loading state.
- To see what happens when a session ends, open the app with `?mock-reset`. The stored token is then unknown to the mock, and the app opens the login page.
- A `403` never signs the user out. See [Handle a 403 on a page](/developer-guide/access-control#handle-a-403-on-a-page).

### In unit tests

`createTestMockApi()` signs in as the first seeded administrator and adds its token to every request that has none. Pass `signedInAs: 'employee'` to send requests as an employee, or `signedInAs: null` to send them without a session, for example to test sign-in.
