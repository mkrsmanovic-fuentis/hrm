Users sign in with email and password and get a session token. The frontend sends the token with every API call. The mock API checks it on every endpoint except sign-in, sign-out and the invite and password reset links, as the real backend must.

New users set their first password through an invite link, and anyone can reset a forgotten password through a reset link. Both sign the user in. See [Invite links and password resets](#invite-links-and-password-resets).

## Demo accounts

Every seeded user who has set a password signs in with the same demo password:

```text
demo-2026
```

The login page offers two of them for one-click sign-in, and the user menu switches between them:

| Role | Name | Email |
| - | - | - |
| Administrator | Maja Novak | `maja.novak@brightwater.example` |
| Employee | Amelia Hughes | `amelia.hughes@brightwater.example` |

Other seeded users sign in with the same password, for example `daniel.brooks@brightwater.example` (the second administrator). These cannot sign in:

- Users with a pending or expired invite, such as `aisha.khan@brightwater.example`. They have no password yet, so they get **Wrong email or password**.
- Deactivated users, such as `sofia.lindqvist@brightwater.example`. With the right password they get **Account deactivated**.

A user who sets a password through an invite or reset link signs in with that password from then on, not the demo password. If you reset a demo account's password, open the app with `?mock-reset` to bring the demo password back.

The demo password and the two accounts are set in `environment.demo` in `src/environments/environment.ts`. The mock's password is `DEMO_PASSWORD` in `src/mocks/seed/people.seed.ts`. A test checks that both demo accounts can sign in. Set `environment.demo` to `null` to hide the demo section and the role switch, for example with a real backend.

## How it works

<Steps>
  <Step title="Sign in">
    The login page (`src/app/features/login/`) calls [`POST /auth/session`](/api-reference/overview#authentication) with the email and password. The answer is a `Session`: the token, when it was created, when it expires, and the signed-in user. Then it opens the `returnUrl`, or the user's home page. A `returnUrl` in the other role's area, or `/no-access`, also opens the user's home page instead of **No access**, for example when an employee signs in where an administrator's session ended.
  </Step>
  <Step title="The session is kept in the browser">
    `AuthService` (`src/app/core/auth/auth.service.ts`) stores the session in `localStorage` under `hrm.session`, so it survives a reload. On load, a session past its `expiresAt` is dropped.
  </Step>
  <Step title="The token goes with every API call">
    `authInterceptor` adds `Authorization: Bearer <token>` to every request to the API base URL. Other requests, such as assets, get no token.
  </Step>
  <Step title="A 401 signs the user out">
    When any API call answers `401`, the interceptor calls `AuthService.endSession()`, which clears the session and opens `/login?returnUrl=<current page>`. After signing in, the login page returns there. The failed sign-in itself also answers `401`; the interceptor leaves that one to the login page.
  </Step>
  <Step title="The session ends on time, even on an open page">
    `AuthService` sets a timer for the session's `expiresAt`. When it fires, it calls `endSession()`: the session is cleared and `/login?returnUrl=<current page>` opens, even if the user is only reading a page.

    The current page is always the URL in the address bar (`addressBarUrl()`), never `router.url`. On the **No access** page the router's URL is `/no-access`, while the address bar shows the page the user opened, which is where they should return.
  </Step>
  <Step title="Tabs share the session">
    Every tab of the app reads the same `hrm.session`. `AuthService` listens to the browser's `storage` event, so a change in one tab reaches the others:

    | In one tab | The other tabs |
    | - | - |
    | Sign out, or the session expires | Sign out and open `/login?returnUrl=<current page>`. |
    | Sign in, or switch the demo role | Take over the new session and check the page in the address bar again: it stays open if the new role may see it, otherwise the new role's home page opens. A tab showing **No access** opens the page once the new role may see it. |

    In the mock, the tabs also share the mock data, so every tab knows the sessions the others started. See [Several tabs share the data](/developer-guide/mock-api#several-tabs-share-the-data).

    When another tab signs in while this tab shows the login page, this tab opens the login page's `returnUrl`, as if it had signed in itself.
  </Step>
  <Step title="Guards protect the routes">
    `signedInGuard` sends signed-out users, and users whose session has expired, to `/login`. `signedOutGuard` sends signed-in users from `/login` to their home page. Every page behind sign-in is a child of the shell route in `src/app/app.routes.ts`, which runs `signedInGuard` on every navigation. `roleGuard` keeps each role to its own area; see [Roles and access](/developer-guide/access-control).
  </Step>
  <Step title="The shell checks the session once per load">
    The shell calls `GET /auth/session` when it starts. If the API no longer knows the token, for example after a mock reset, the `401` signs the user out.
  </Step>
  <Step title="Sign out">
    The user menu calls `DELETE /auth/session`, then clears the session locally and opens `/login`. The session ends locally even if the call fails.
  </Step>
</Steps>

### Use it in a feature

Read the signed-in user and role from `AuthService` signals. Import from `core/auth`.

```ts
private readonly auth = inject(AuthService);

readonly user = this.auth.user;   // Signal<User | null>
readonly role = this.auth.role;   // Signal<'administrator' | 'employee' | null>
```

After changing the signed-in user's own record, pass the API's answer to `updateUser()`, so the top bar shows the new name and email at once. The Employees page does this after an administrator edits themselves. It ignores any other user, and other tabs pick up the change too.

```ts
const saved = await firstValueFrom(this.api.patch('/users/{userId}', { path, body }));
this.auth.updateUser(saved);
```

Pages behind sign-in need no extra code for sign-in: add them to a role's area and the guards cover them. See [How a feature adds a page and a nav entry](/developer-guide/access-control#how-a-feature-adds-a-page-and-a-nav-entry).

### Role switch for demos

**Switch to employee** and **Switch to administrator** in the user menu sign out, then sign in as the demo account of the other role, and open that role's home page. They appear only when `environment.demo` has an account for the other role.

## Invite links and password resets

The pages are public: they live outside the shell in `src/app/features/password/`, next to the login page, and use the same layout (`src/app/shared/auth-page/`).

| Page | Component | Guard |
| - | - | - |
| `/set-password?token=…` | `ChoosePassword`, with route `data.purpose` set to `invitation` | None. Someone who is signed in can still open a link. |
| `/reset-password?token=…` | `ChoosePassword`, with `data.purpose` set to `password_reset` | None. |
| `/forgot-password` | `ForgotPassword` | `signedOutGuard`. The login page links to it with **Forgot password?**. |

<Steps>
  <Step title="The link is checked when the page opens">
    `ChoosePassword` reads `token` from the URL and calls [`GET /auth/invitations/{invitationToken}`](/api-reference/overview#authentication) or `GET /auth/password-resets/{passwordResetToken}`. A valid link returns the user's email and first name for the form. A link that has expired (`410 /problems/link-expired`), was used (`410 /problems/link-used`) or is unknown (`404 /problems/link-not-found`) shows an `sd-callout` with what to do next. A URL without a token counts as unknown.
  </Step>
  <Step title="The user types the password twice">
    The form checks the [password rules](/developer-guide/business-rules#passwords) that the API checks, and that both entries match. Only the password is sent.
  </Step>
  <Step title="Setting the password signs the user in">
    `AuthService.acceptInvitation()` or `AuthService.resetPassword()` sends the password. The API answers with a new `Session`, which `AuthService` keeps as after signing in. The page shows a toast and opens `/`, the user's home page. If someone else was signed in in this browser, the new session replaces theirs in every tab.

    A reset ends all the user's other sessions in the API. Their other tabs and devices get `401` on their next call and open the login page.
  </Step>
  <Step title="Forgot password always answers the same">
    `ForgotPassword` sends `POST /auth/password-resets` and always shows **Check your email**, with the same text for every email.

    The login page's `returnUrl` goes along to **Forgot password?** and back with **Back to sign in**. The emailed reset link does not carry it. A set or reset page opened with a `returnUrl` keeps it on its links and opens it after success, through `safeReturnUrl()`.
  </Step>
</Steps>

### Demo links instead of email

The demo sends no email. The mock API returns the link it would have emailed in the `X-Demo-Link` response header, documented in the spec as demo only:

| Request | Header |
| - | - |
| `POST /users` | The new user's invite link. |
| `POST /users/{userId}/invitation` | The new invite link. |
| `POST /auth/password-resets` | The reset link, only when one was created. |

**The mock sends the header only while `environment.demo` is set.** `src/mocks/browser.ts` passes `demoLinks: environment.demo !== null` to the mock, and handlers add the header through `demoLinkHeader(ctx, link)`, which adds nothing while `ctx.demoLinks` is off. With `environment.demo` set to `null`, the links never leave the mock, as with the real backend: otherwise anyone could read a working reset link for any email from the response headers. In unit tests, `createTestMockApi({ demoLinks: false })` turns the header off; it is on by default.

`ApiClient.postWithHeaders()` returns the body and the headers, and `demoLinkOf()` from `core/api` reads the link. Pages show it with `<app-demo-link>` from `src/app/shared/demo-link/`, an `sd-callout` labelled **Demo only** with a read-only field and a copy button, and only while `environment.demo` is set, like the demo accounts. Set `environment.demo` to `null` and the mock sends no links and the pages show none.

The demo data lives in the browser's IndexedDB, so a link works only in the browser that created it. Open it in a new tab of the same browser. Setting the password there signs that browser in as the link's user, in every tab, replacing the administrator's session.

- The Employees page shows the invite link above the list after creating a user or sending the invite again.
- The **Check your email** page shows the reset link under the confirmation, when the mock created one.

### See a link expire

Move the mock's clock with the `mock-clock` flag, scoped to the link endpoints so your own session stays valid. Add it to the link's URL:

```text
/reset-password?token=…&mock-clock=2h&mock-scope=/auth/password-resets
/set-password?token=…&mock-clock=8d&mock-scope=/auth/invitations
```

The page shows **This reset link has expired** or **This invite link has expired**. Open the app with `?mock-clear` to stop.

The clock also moves sessions, so to see **Invite expired** on the Employees page, look at the seeded Samuel Adeyemi instead: his invite expired in the seed. He has no link; send the invite again to get one. See [Simulate slow responses, errors and empty lists](/developer-guide/mock-api#simulate-slow-responses-errors-and-empty-lists).

## Rules

- A session lasts 8 hours from sign-in. Activity does not extend it.
- Only active users who have set a password can sign in.
- Invite links last 7 days, reset links 1 hour and work once, and a password has at least 12 characters. See [Invite links and password resets](/developer-guide/business-rules#invite-links-and-password-resets) and [Passwords](/developer-guide/business-rules#passwords).
- See [Business rules](/developer-guide/business-rules#sign-in-and-sessions) for the full list, including what the real backend must do.

## Mock behavior

| Request | Answer |
| - | - |
| `POST /auth/session`, right email and password | `201` with the session. Updates the user's `lastSignedInAt`. The right password is the one the user set through a link, or the demo password if they never set one. |
| `POST /auth/session`, wrong password, unknown email, or no password set yet | `401`, type `/problems/invalid-credentials`. |
| `POST /auth/session`, deactivated user with the right password | `403`, type `/problems/account-inactive`. |
| `POST /auth/session`, missing email or password, or an email without `@` | `422`, with every invalid field in `errors`. |
| `GET /auth/session` with a valid token | `200` with the session. |
| `DELETE /auth/session` | `204`, with or without a valid token. The token stops working. |
| `GET /auth/invitations/{invitationToken}`, `GET /auth/password-resets/{passwordResetToken}` | `200` with the email, first name and expiry. `410` expired or used, `404` unknown, replaced or deactivated user. |
| `POST /auth/invitations/{invitationToken}/password` | `201` with a new session. Sets `passwordSetAt`, clears the invitation fields, uses up the link. |
| `POST /auth/password-resets/{passwordResetToken}/password` | `201` with a new session, after deleting every other session of the user. |
| Either `POST …/password` with a password that breaks the rules | `422` on `password`. The link still works. |
| `POST /auth/password-resets` | `202` with no body for any valid email. Only for an active user with a password does it create a link, and adds `X-Demo-Link` while demo links are on. `422` for a missing or malformed email. |
| `POST /users` and `POST /users/{userId}/invitation` | Add the invite link in `X-Demo-Link` while demo links are on. Sending again removes the old link, so it answers `404`. |
| `PATCH /users/{userId}` that deactivates the user | Also removes all their invite and reset links. They answer `404`, and stay gone after reactivating. |
| `PATCH /users/{userId}` that changes the email | Also removes the user's reset links. |
| Any other endpoint without a token, with an unknown token or with an expired one | `401`, type `/problems/unauthenticated`. |

- Links are stored in the `accountLinks` table and passwords, as SHA-256 hashes, in `credentials`. Both start empty in the seed. The helpers are in `src/mocks/support/account-links.ts`, the rules in `src/mocks/rules/auth-rules.ts`.
- Sessions are stored in the `sessions` table of the mock database, so they survive a reload. `?mock-reset` empties it, which signs everyone out on their next API call.
- Simulation flags apply to the authentication endpoints too. `?mock-error=server` also makes sign-in fail. To test errors on one area while staying able to sign in, add a scope, for example `?mock-error=server&mock-scope=/topics`.
- `?mock-delay=2000&mock-scope=/auth` slows down sign-in, to see the loading state.
- To see what happens when a session ends, open the app with `?mock-reset`. The stored token is then unknown to the mock, and the app opens the login page.
- A `403` never signs the user out. See [Handle a 403 on a page](/developer-guide/access-control#handle-a-403-on-a-page).

### In unit tests

`createTestMockApi()` signs in as the first seeded administrator and adds its token to every request that has none. Pass `signedInAs: 'employee'` to send requests as an employee, or `signedInAs: null` to send them without a session, for example to test sign-in.
