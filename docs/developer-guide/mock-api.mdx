The frontend makes real HTTP calls to `/api/v1`. While there is no backend, [Mock Service Worker](https://mswjs.io) (MSW) answers them in the browser with dummy data. The mock follows the [API spec](/api-reference/overview) and the [business rules](/developer-guide/business-rules), so the frontend behaves as it will with the real backend.

## How it works

<Steps>
  <Step title="The mock starts before the app">
    `src/main.ts` starts the mock, waits until its service worker is ready, then bootstraps Angular. The very first request is already mocked. The mock is on while `mockApi` is `true` in `src/environments/environment.ts`, which is always for now.
  </Step>
  <Step title="Components call the API client">
    Features call `ApiClient` from `src/app/core/api/`. It sends real requests through Angular's `HttpClient`. Components never use `HttpClient` directly.
  </Step>
  <Step title="The service worker hands the request to a handler">
    A handler in `src/mocks/resources/` reads or changes the mock database and answers in the format the spec describes, including errors.
  </Step>
  <Step title="Changes are saved in the browser">
    Each tab keeps the mock database in memory. After every request that changed it, the mock saves it to the browser's IndexedDB (database `hrm-mock-api`), so data survives a page reload.
  </Step>
</Steps>

Requests to `/api/v1` that no handler knows get a `404` problem that names the missing handler. Other requests, such as scripts and images, go to the network as usual.

Mocked requests appear in the browser's network panel as normal requests, answered by the service worker.

## Seed data

On first load, and after a reset, the mock database is filled from the seed in `src/mocks/seed/`. The seed is generated from a fixed random seed, so it is the same everywhere. Dates are relative to the moment it was created, so deadlines stay realistic.

| Data | What the seed has |
| - | - |
| Organization | Brightwater Logistics, a fictional company. |
| Departments | 9, one of them inactive. |
| Users | 42: 2 administrators (Maja Novak and Daniel Brooks) and 40 employees. 3 are inactive, 2 have a pending invite and 1 has an expired invite. 2 have no department. Emails end in `@brightwater.example`. |
| Topics | 8: the 7 topics from the FRD (Phishing Awareness, Password Security, Data Protection, Social Engineering, Safe Internet Usage, Device Security and Remote Work Security), and Clean Desk Policy, which is inactive and has no questionnaires, so employees see one topic fewer than administrators. |
| Questionnaires | 11. 10 with 3 to 5 questions each, passing scores of 70, 80 and 90, some with a time limit; one of them is inactive. "Spotting phishing emails" has two versions, and attempts on both. "Reporting suspicious messages" is an inactive draft with an empty version 1 and no assignments, so it cannot be activated. |
| Assignments | About 120, in every status: Not Started, In Progress, Passed, Failed and Overdue. Includes retakes, late passes and attempts submitted by the time limit. |
| Notifications | New assignments and deadline reminders, some read. |
| Audit log | Creation of every department, topic, questionnaire, employee and assignment, plus edits and deactivations. |

## Sign in to the mock

Every endpoint except sign-in and sign-out needs a session token, as with the real backend. Seeded users sign in with the demo password `demo-2026`. The demo accounts, the session rules and how the mock answers are on the [Authentication](/developer-guide/authentication) page.

## Several tabs share the data

Tabs of the app share the mock data, as if they used one backend. For each request, the mock:

1. Takes a Web Lock that all tabs share, so only one request runs at a time across tabs.
2. Loads the stored data if another tab saved since this tab last did.
3. Runs the handler.
4. Saves the changes, then releases the lock.

So a session or record that one tab creates is there for the next request in any tab, and no tab overwrites another tab's change. The data is kept in IndexedDB, not `localStorage`: right after one tab writes to `localStorage`, another tab can still read the old value, and its next save would undo the change.

Handlers need nothing extra for this: read `db.data` and change it in `db.update()`, as usual. Tests can share data between two mock APIs by passing the same `MemoryMockStore` from `src/mocks/db/mock-store.ts` as `store`; `src/mocks/support/mock-route.spec.ts` does this.

## Reset the data

Any of these restores the seed and throws away every change:

- Open the app with `?mock-reset`, for example `http://localhost:4200/?mock-reset`. The parameter is removed from the address after the reset, so a reload keeps your next changes.
- Run `hrmMockApi.reset()` in the browser console. It resets and reloads the page.
- Clear the site data for `localhost:4200` in the browser. This also signs you out.

A reset in one tab applies to every tab on its next request.

When the seed or the shape of stored records changes, bump `SEED_VERSION` in `src/mocks/seed/seed.ts`. Browsers holding older data then start again from the new seed.

In the console, `hrmMockApi.data()` returns the current mock data and `hrmMockApi.flags` the active simulation flags.

## Simulate slow responses, errors and empty lists

Add flags to the app's address to see loading, error, access-denied and empty states without changing code:

| Flag | Effect |
| - | - |
| `mock-delay=1500` | Waits 1,500 ms before every response. `mock-delay` or `mock-delay=slow` waits 3 seconds. |
| `mock-error=server` | Every request fails with `500`. |
| `mock-error=forbidden` | Every request fails with `403`, access denied. |
| `mock-error=unauthenticated` | Every request fails with `401`, not signed in. |
| `mock-error=not-found`, `conflict`, `validation`, `bad-request` | `404`, `409`, `422` and `400`. Any status from 400 to 599 also works, for example `mock-error=503`. |
| `mock-empty` | List endpoints return no items. |
| `mock-scope=/topics` | Applies the other flags only to API paths that start with `/topics`, for example `/topics` and `/topics/{topicId}`. |
| `mock-clear` | Turns all flags off. |

Flags can be combined, for example `http://localhost:4200/?mock-error=forbidden&mock-scope=/topics`.

Flags stay on for the browser tab, even after navigating or reloading, until you open the app with `mock-clear` or close the tab. Opening the app with new flags replaces the old ones. The console shows which flags are active when the app loads.

Simulated errors use the same problem format as real ones. Without flags, every response has a short random delay, so loading states are visible briefly.

## Add an endpoint

Follow these steps, in this order, in the same pull request as the feature.

<Steps>
  <Step title="Describe the endpoint in the spec">
    Add the path, parameters, request body and responses to `docs/api-reference/openapi.yaml`, following the [conventions](/api-reference/overview#conventions). Add new schemas under `components.schemas`, and update the [Data model](/developer-guide/data-model) page.
  </Step>
  <Step title="Generate the types">
    Run `pnpm api:types`. It writes `src/app/core/api/api-schema.gen.ts`. Commit it. `pnpm check` fails when the file does not match the spec.
  </Step>
  <Step title="Call it through the API client">
    Paths, parameters, bodies and responses are checked against the spec. Wrong paths or missing parameters do not compile.

    ```ts
    private readonly api = inject(ApiClient);

    readonly topics = this.api.get('/topics', { query: { status: 'active', page: 1 } });
    readonly topic = this.api.get('/topics/{topicId}', { path: { topicId } });
    ```

    Calls fail with an `ApiError`. Use `error.isForbidden`, `error.isNotFound`, `error.isValidation` and `error.fieldErrors` to show the right state.
  </Step>
  <Step title="Add a mock handler">
    Create `src/mocks/resources/<resource>/<resource>.handlers.ts` and add its routes to `mockRoutes` in `src/mocks/handlers.ts`. `route` takes the path exactly as in the spec, and the body passed to `ok()` must match the spec's response type.

    ```ts
    export const topicRoutes = [
      route.get('/topics', ({ db, query, page, ok, validationFailed }) => {
        const pagination = query.pagination();
        const status = query.oneOf('status', ['active', 'inactive'] as const);
        if (query.errors.length > 0) return validationFailed(query.errors);

        const topics = db.data.topics.filter((t) => !status || t.status === status);
        return ok(page(topics, pagination));
      }),
    ];
    ```

    - Check the role first. Administrator endpoints call `requireRole(ctx, 'administrator')`; records that belong to a user go through `ownRecords()` or `requireOwnRecord()`. See [How a handler requires a role](/developer-guide/access-control#how-a-handler-requires-a-role).
    - Validate every parameter and body field the spec constrains, and answer `validationFailed()` with all problems at once. `ctx.query` reads query parameters; `BodyReader` from `src/mocks/support/body.ts` reads a JSON body the same way, trims text and rejects unknown fields.
    - Answer a value already used by a unique field with `throw notUnique(field, message, detail)` from the same file: a `409` that names the field.
    - Use `notFound()`, `problem(status, detail)` or throw `MockProblem` for other errors.
    - Change data only inside `db.update()`, so it is saved when the request ends.
    - Apply business rules from `src/mocks/rules/`. Add a rule there when you need a new one, mirrored from [Business rules](/developer-guide/business-rules).
    - Return lists through `page()`, so paging and the `mock-empty` flag work.
    - In administrator handlers that create, edit, deactivate or reactivate a record, log the action. See [Record the audit log](#record-the-audit-log).
  </Step>
  <Step title="Extend the seed if needed">
    If the resource needs new data, add it to the seed in `src/mocks/seed/` and the table to `MockData` in `src/mocks/db/mock-data.ts`. Keep it realistic and deterministic: use `SeededRandom`, never `Math.random()`. Bump `SEED_VERSION`.
  </Step>
  <Step title="Test the handler">
    Add `<resource>.handlers.spec.ts` next to the handler. `createTestMockApi()` from `src/mocks/testing.ts` runs the same handlers and seed in memory, with no delay and a fixed date. Its `providers` connect `HttpClient`, and so `ApiClient`, to the handlers. Its `fetch()` calls a handler directly.

    ```ts
    const mock = createTestMockApi({ flags: { errorStatus: 403 } });
    TestBed.configureTestingModule({ providers: [provideHttpClient(), ...mock.providers] });
    ```

    Test the endpoint as both roles: `createTestMockApi({ signedInAs: 'employee' })` sends requests as an employee. `src/mocks/resources/topics/topics.handlers.spec.ts` is a complete example of a read endpoint, and `src/mocks/resources/departments/departments.handlers.spec.ts` of create and edit endpoints.
  </Step>
</Steps>

## Record the audit log

Every administrator handler that creates, edits, deactivates or reactivates a record calls `recordAudit()` from `src/mocks/db/audit.ts`, inside the same `db.update()` as the change. It fills in the `changes` list from the records before and after, and adds the entry to the mock database. The [audit log rules](/developer-guide/business-rules#audit-log) say which actions are logged and what each entry holds.

```ts
// Inside an edit handler, after validating the body and finding the stored department.
// `changes` holds the fields the request sent, status included.
const updated = db.update((data) => {
  const before = structuredClone(department);
  Object.assign(department, changes);
  const entries = recordAudit(data, {
    action: 'updated',
    entityType: 'department',
    actorId: admin.id,
    now,
    before,
    after: department,
  });
  if (entries.length > 0) department.updatedAt = now.toISOString();
  return department;
});
```

- `created` takes `after`, the new record, and logs one entry.
- `updated` takes `before` and `after`. Pass every edit as `updated`, also one that changes `status`: changed fields other than `status` are logged as one `updated` entry, then a change of `status` as `deactivated` or `reactivated`. An edit that changes nothing logs nothing.
- `deactivated` and `reactivated` take `after`, for handlers that only change the status.
- `recordAudit()` returns the entries it added, in order. An empty list means nothing changed, so leave `updatedAt` as it is.
- Values are compared by content, regardless of the order of object keys.
- Pass stored records, not API responses. Derived fields, such as `employeeCount`, are never listed in `changes`; `recordAudit()` throws when a record carries one. The derived fields of each record type are `DERIVED_FIELDS` in `src/mocks/db/mock-data.ts`, and the stored record types leave them out.
- `actorId` is the signed-in administrator. `requireRole(ctx, 'administrator')` returns that user.
- Assigning to a department creates many assignments: call `recordAudit()` once for each.

## Switching to a real backend

When a backend implements the spec, set `mockApi` to `false` in `src/environments/environment.ts`. The mock is loaded only when it is on, so it then drops out of the build. Nothing else in the frontend changes.
