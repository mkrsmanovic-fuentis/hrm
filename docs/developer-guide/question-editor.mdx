The **Questions** section of the questionnaire page at `/admin/questionnaires/{questionnaireId}` is the question editor. Administrators add, edit, remove and reorder questions and answer options there, and save the whole list at once.

## How it works

<Steps>
  <Step title="The editor loads the current version">
    `GET /questionnaires/{questionnaireId}/questions` returns the current `QuestionnaireVersion`, with its questions and answer options in display order, and its derived `attemptCount`.
  </Step>
  <Step title="Edits change a working copy">
    The editor copies the questions into a signal and changes only that copy. Nothing is sent while editing. The copy is compared with the saved questions, after trimming, to show **Unsaved changes** and enable **Save questions**.
  </Step>
  <Step title="Saving checks the copy first">
    The editor checks the same rules as the API: text is required, within its limits, and an active questionnaire must be complete. Problems show on their fields, and nothing is sent.
  </Step>
  <Step title="A new version is confirmed first">
    When `attemptCount` is above 0, saving creates a new version. The editor says so in a callout above the questions and asks in an `<app-confirm-dialog>` before it sends the save.
  </Step>
  <Step title="The whole list is sent at once">
    `PUT /questionnaires/{questionnaireId}/questions` with `{ questions: [...] }` replaces the questions. The answer is the current version after the save, which becomes the editor's new saved state. The page then reloads the questionnaire, so the question count is up to date.
  </Step>
</Steps>

Saving the whole ordered list makes a save one change: either the current version's questions are replaced, or one new version is created. There are no endpoints for single questions.

## The editor

| Part | ui-kit | Notes |
| - | - | - |
| Section | `sd-panel` | One `sd-panel-section` for the summary and actions, one per question, and one for the buttons at the end. |
| Text fields | `sd-field` with `input[sd-input]` or `textarea[sd-input]` | Errors are keyed by the API's field names, for example `questions[2].answerOptions[0].text`, so client and API errors land in the same place. |
| Correct answer | `sd-select` | One value from the question's answer options, so only one can be correct. The correct option also shows an `sd-badge` **Correct**. |
| Move and remove | `button[sd-button]` with `iconOnly` | Each has an `aria-label` such as "Move question 2 up". At the top or bottom, the move button is disabled. |
| Version notice | `sd-callout` `tone="info"` | Shown while `attemptCount` is above 0. |
| Confirmations | `<app-confirm-dialog>` | Save as a new version, discard changes, and leave without saving. |
| Feedback | `ToastService` | **Questions saved**, or **Version N created** when a new version was made. |

The editor uses plain signals for the working copy, not signal forms, because questions and answer options are nested lists that change shape while editing.

### Keyboard and screen readers

- Every action is a native button, reachable with Tab.
- After a move, focus stays on the moved item's move button, or on the other one when it reached the top or bottom, so the item can be moved again. A polite live region says what moved, for example "Question 3 moved to position 2."
- After adding a question or an answer option, focus goes to its text field. After removing one, focus goes to the next item, or to the add button.
- After a save with errors, focus goes to the first invalid field.

Drag and drop is not built. The up and down buttons do the same and work with the keyboard.

### Unsaved changes

- **Leaving the page in the app**: the questionnaire route has `canDeactivate: [unsavedChangesGuard]`. The guard asks the page's `confirmLeave()`, which asks the editor. With unsaved changes, the editor opens **Leave without saving?** and resolves `false` on **Keep editing** or a dismissed dialog, `true` on **Leave without saving**.
- **Closing or reloading the tab**: the editor handles `beforeunload` and calls `preventDefault()` while there are unsaved changes, so the browser asks.

Another page with unsaved changes can reuse the guard: implement `LeaveConfirmation` and add the guard to its route.

## Mock behavior

| Request | Answer |
| - | - |
| `GET /questionnaires/{questionnaireId}/questions` | `200` with the current version, its questions, answer options and `attemptCount`. |
| `PUT …/questions`, no attempt uses the current version | `200`. The version's questions are replaced in place. Logged as `updated` with `questions`. |
| `PUT …/questions`, attempts use the current version | `200` with a new version, number plus one. `currentVersionId` points to it. Earlier versions and attempts are unchanged. Logged as `updated` with `currentVersionId` and `questions`. |
| `PUT …/questions` with the same questions as now | `200` with the current version. Nothing is saved or logged. |
| An active questionnaire left without questions, or with a question that has fewer than two answer options or not exactly one correct | `422`. `errors` names `questions` or `questions[i].answerOptions`. |
| Empty or too long text, a value of the wrong type, an unknown field | `422` with every invalid field, for drafts too. |
| An unknown questionnaire | `404`. |
| Either endpoint as an employee | `403`, before the body is read. |

In the seed, every active questionnaire has attempts, so editing one creates a new version. "Spotting phishing emails" is at version 2, so a save creates version 3. To edit in place, create a questionnaire, add questions and save, or edit the draft "Reporting suspicious messages".
